# Releasing

Releases are tag-driven. Push a `v*` tag and
[`.github/workflows/release.yml`](./.github/workflows/release.yml) builds, verifies,
publishes to PyPI and opens a GitHub Release.

## One-time PyPI setup (trusted publishing)

No API token is stored anywhere. PyPI verifies a short-lived OIDC token GitHub mints for
this specific repository + workflow + environment, so there is no long-lived secret to
leak or rotate.

On [pypi.org](https://pypi.org) → your project → **Publishing** → *Add a new pending
publisher*:

| Field | Value |
|-------|-------|
| Owner | `pip-install-python` |
| Repository | `dash-emoji-mart` |
| Workflow name | `release.yml` |
| Environment name | `pypi` |

The repository name is **hyphenated**. The repo was renamed from `dash_emoji_mart`;
GitHub redirects the URL but OIDC does **not** redirect the claim, so a publisher entry
holding the old underscore name fails with an opaque 403 at upload time.

The environment name must match the `environment:` block in `release.yml`. Add a required
reviewer on that environment in the repository settings if you want a human approval gate
between the tag and the upload.

## Cutting a release

### 1. Bump the version — in all four places

The version lives in four files and `scripts/check_release.py` fails if they disagree:

| File | Field |
|------|-------|
| `pyproject.toml` | `version = "..."` |
| `package.json` | `"version": "..."` |
| `dash_emoji_mart/package-info.json` | regenerated by `npm run build:backends` |
| `lib/constants.py` | `APP_VERSION = "..."` |

Bump `pyproject.toml`, `package.json` and `lib/constants.py` by hand, then run
`npm run build` — `build:backends` copies `package.json` into `package-info.json`, which is
where `dash_emoji_mart.__version__` is read from at import.

### 2. Write the changelog entry

Add a `## [x.y.z] — YYYY-MM-DD` section to [CHANGELOG.md](./CHANGELOG.md) and a link
reference at the bottom. `check_release.py` fails without a section for the version being
released, and `release.yml` extracts that exact section as the GitHub Release body.

### 3. Verify locally

```bash
npm run build
python scripts/check_release.py
python scripts/smoke_test.py
python -m build && python -m twine check dist/*
```

### 4. Commit, tag, push

```bash
git add -A
git commit -m "Release 0.2.0"
git tag v0.2.0
git push origin main --tags
```

The tag **must** match `pyproject.toml` — `release.yml` refuses to publish a mismatch,
which is the classic way a release goes out with the wrong number.

### 5. Watch the workflow

`release.yml` runs four jobs in sequence:

1. **verify** — the tag matches `pyproject.toml`, and `check_release.py` passes.
2. **build** — smoke test against the current Dash, then `python -m build` + `twine check`.
3. **publish** — uploads to PyPI via OIDC.
4. **github-release** — extracts the changelog section and attaches the artifacts.

## Dry run

To exercise everything without touching PyPI, run the workflow manually from the Actions
tab with **dry_run** checked. It publishes to TestPyPI instead:

```bash
pip install -i https://test.pypi.org/simple/ dash-emoji-mart
```

## Vendored consumers

`dash-leaflet2` vendors this package as a tarball in its `vendor/` directory (its
`/emoji-iconify` and `/easy-button` pages depend on it). After publishing, update it there:

```bash
cd ../2plot_leaflet
rm vendor/dash_emoji_mart-*.tar.gz
# then either point requirements.txt at PyPI:
#   dash-emoji-mart>=0.2.1
# or drop in the new sdist and update the ./vendor/... line
```

Once 0.2.1 is on PyPI the vendored tarball should go away entirely — it existed because
PyPI's 0.0.3 was broken under Dash 4.

## Documentation site

The docs deploy separately, from `main`, via the Render Blueprint in
[render.yaml](./render.yaml) with `autoDeploy: true`. A release does not have to coincide
with a docs deploy, but the site's `lib/constants.APP_VERSION` is one of the four version
sources, so in practice they move together.
